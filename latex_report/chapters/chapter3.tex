\chapter{Design}

The design phase translates the requirements identified during the system study into a structured representation of the proposed CricketVision system. It defines the overall architecture, functional interactions, data flow, database organization, and user interface structure of the application. The design is intended to provide a clear separation between the different components of the system while allowing the application to be extended with additional functionality in future development.

CricketVision follows a modular web application architecture in which the user interacts with a React-based frontend, authentication is handled through role-based access controllers, and player data is stored using MongoDB with Mongoose ODM. The design also considers protected access to user-specific resources so that performance records are associated with appropriate authenticated roles.

\section{System Architecture}

The system architecture describes the major components of CricketVision and the manner in which they interact. The system consists primarily of the presentation layer, routing layer, authentication layer, application service layer, and data layer.

The frontend is implemented using React and provides the user interface through which coaches, players, and analysts interact with the system. React Router is used to manage navigation between different application pages. Protected routes are used for resources that require authentication.

Authentication services handle user registration, login, preset switching, and logout operations. Once a user is authenticated, the application can identify the corresponding persona and display role-restricted resources.

MongoDB provides database storage for player information. The Express backend exposes RESTful CRUD endpoints allowing the client application to query or update player documents.

The major components of the architecture are described below:

\begin{enumerate}
    \item \textbf{Presentation Layer:} Provides the user interface using React components, Recharts visualizations, and Tailwind CSS.
    \item \textbf{Routing Layer:} Manages navigation between pages and protects authenticated routes using React Router.
    \item \textbf{Authentication Layer:} Provides user registration, login, logout, and role-state management.
    \item \textbf{Application Service Layer:} Handles operations related to player statistics, match simulations, and pose estimations.
    \item \textbf{Data Layer:} Uses MongoDB to store player records and user accounts.
\end{enumerate}

\section{Use Case Design}

Use case modelling describes the functional interactions between sports professionals and the CricketVision system. The primary actors of the system are the \textbf{Head Coach}, \textbf{Elite Player}, and \textbf{Sports Analyst}.

The major use cases identified for the system are:

\begin{itemize}
    \item Register
    \item Login
    \item Logout
    \item View Dashboard
    \item Add Player / Record
    \item View Player Analytics

\subsection{Register}
The Register use case allows a new user to create an account. The user provides the required authentication details, which are validated by the backend service. Upon successful registration, an account is created.

\subsection{Login}
The Login use case allows a registered user or persona preset to access the system. The authentication credentials are submitted to the authentication controller. If valid, the user is authenticated and granted access to protected resources.

\subsection{View Dashboard}
The Dashboard provides the main authenticated interface of the application. It displays squad overview statistics, fatigue alerts, and recent player performance metrics.

\subsection{Add Player}
The Add Player use case allows the coach to create a new player entry. The user enters details such as player name, country, playing role, fatigue level, and skill attributes, which are stored in MongoDB.

\subsection{View Analytics}
The View Analytics use case allows users to view 360-degree wagon wheel shot dispersion heatmaps, Recharts radar attribute charts, and phase-wise statistical breakdowns.

\subsection{Edit Player Profile}
The Edit Player use case allows a coach to modify an existing player record when fatigue levels change or new match stats are recorded.

\subsection{Delete Player Record}
The Delete Player use case allows a coach to remove a player profile from the active roster database.

\subsection{Logout}
The Logout use case terminates the active authenticated session and prevents further access to protected resources until the user authenticates again.

\section{Database Design}

CricketVision uses MongoDB with Mongoose as its database engine. Information is organized in document collections:

\begin{lstlisting}
users
|
+-- {userId}
      +-- name, email, role, permissions

players
|
+-- {playerId}
      +-- name, country, role, fatigueLevel, clutchRating, skillRadar, phaseStats
\end{lstlisting}

The main fields of a player document are described in Table 3.1.

\section{User Interface Design}

The user interface is designed using React components and Tailwind CSS. The major interfaces include the home page, login/registration page, dashboard, and player management forms.

\subsection{Home Page}
The home page provides an introduction to CricketVision and navigation to login and portal selector controls.

\subsection{Login and Registration Interfaces}
The login interface allows users to authenticate using credentials or persona presets.

\subsection{Dashboard}
The dashboard acts as the primary interface after authentication, displaying squad KPIs, fatigue alerts, and player lists.

\subsection{Add Application Form / Add Player Form}
The form contains fields for player name, country, playing role, fatigue level, and performance metrics.

\section{Security Design}

Security is implemented through role-based authorization controllers, password validation, and protected frontend routes. Protected routes prevent unauthenticated users from directly accessing sensitive pages.

\section{Design Summary}

The design of CricketVision defines the architecture, functional interactions, data flow, database structure, and interface components required for the proposed system. The architecture separates the user interface, backend controllers, and database storage, allowing the system to remain modular and extensible.
